# Приложения ISIVR

Работай через MCP `isivr`. В проекте имя сервера заканчивается на `-isivr`. Не формируй `Template` XML и не вызывай HTTP напрямую:
MCP сохраняет идентификаторы, порты и визуальную схему.

Инструменты MCP: `isivr_operations`, `isivr_call`, `isivr_get_module`, `isivr_save_module`,
`isivr_upload_sound`. Других инструментов ISIVR нет. Операции API ищи через
`isivr_operations`, не по исходному коду.

## Без исходников

Навык и MCP — полный контракт. Не открывай репозиторий платформы: контроллеры, шаблоны
кода дизайнера, скрипты блоков. Если параметра или операции нет в [blocks.md](blocks.md),
[workflow.md](workflow.md) и ответе `isivr_operations`, остановись и назови пробел.
Образец `params` бери из живого модуля через `isivr_get_module`, когда формат в навыке
ещё не записан.

## Перед началом

1. Уточни ожидаемое поведение, точки входа, успешные и аварийные завершения.
2. Найди приложение и версию через `isivr_operations` и `isivr_call`.
3. Для существующего модуля обязательно вызови `isivr_get_module`.
4. Прочитай [blocks.md](blocks.md) для используемых типов блоков.
5. Сверь проект с [patterns.md](patterns.md), но не копируй тестовые значения.
6. Для операций жизненного цикла и форматов вызовов используй [workflow.md](workflow.md).
7. Изучи доступные функции ISIVR (раздел «Функции»): см. «Интеграции через функции» ниже.

## Интеграции через функции

Блок `Function` и справочник «Функции» — единственный способ интегрировать приложение
с внешними системами: CRM, биллинг, проверка клиента, получение EWT, агента и т.д.
Функция — HTTP(s)-запрос с типизированными входными и выходными параметрами,
созданный заранее в справочнике и вызываемый из блока `Function`.

Перед проектированием приложения:

1. Найди функции, подходящие под задачу (см. «Функции» в [workflow.md](workflow.md)).
2. Для каждой выбранной функции изучи назначение, версию, входы, выходы и их типы.
3. Посмотри, как функция уже вызывается в опубликованных приложениях: какие переменные
   передаются и как ветвится результат.
4. Заведи переменные модуля под входы и выходы с совпадающими типами.
5. После `Function` проверяй результат через `Condition` и предусмотри fallback
   на ошибку, пустой ответ или таймаут.

Если подходящей функции нет, не имитируй интеграцию звуками или условиями:
сообщи пользователю, какая функция нужна (адрес, входы, выходы). Создавать или менять
функции можно только по явному запросу — они общие для всех приложений.

## Одно приложение — один модуль

Дополнительные модули и блок `Transfer` (переход к модулю) недоступны. Вся логика
приложения живёт в его корневом модуле. Общий участок, в который ведут несколько веток
(очередь, бот, повтор меню), встраивай один раз под `Marker` и веди в него через `GoTo`.
Если участок самостоятельный или нужен нескольким приложениям, вынеси его в отдельное
приложение и вызови блоком `TransferToApp`. `isivr_save_module` без `id` корневого модуля
и с новым `Transfer` MCP отклоняет.

## Выбор режима

### Новое приложение

1. Создай приложение в статусе разработки.
2. Работай в корневом модуле из ответа `Application_Edit` (`RootModule.ID`).
3. Спроектируй полный граф: блоки, переменные, параметры, переходы.
4. Сохрани через `isivr_save_module` с `layout: "full"`.
5. Проверь ответ `validation` и повторно прочитанный `graph`.

### Редактирование

1. Не изменяй опубликованную или стабильную версию напрямую.
2. Если версия стабильная, клонируй её в рабочее приложение либо создай редактируемую версию — согласно запросу пользователя.
3. Прочитай весь модуль через `isivr_get_module`.
4. Передай обратно полный граф, сохранив неизменённые блоки, рёбра, переменные, `id`, `key` и неизвестные поля `params`.
5. Используй `layout: "keep"` для правок параметров и переходов; `incremental` — при добавлении блоков; `full` — только для явно запрошенной полной перераскладки.

## Проектирование логики

- В модуле ровно один `Start`.
- Метке, на которую ссылаются `GoTo` в том же сохранении, задай явный `cellId` (например, 400, 401) и укажи его в `MarkerBlockCellID`. При полной замене схемы давай новым блокам `cellId`, не совпадающие с текущими ячейками модуля, иначе сохранение упадёт на уникальности ячейки.
- Добавляй `End` для возврата в родительское приложение и `EndCall` для завершения вызова.
- После `AnswerCall` размещай пользовательское взаимодействие: звук, меню, ввод или перевод.
- Для каждого ветвящегося блока подключай штатные и аварийные выходы.
- Создавай переменную до ссылки на неё в `params`; типы должны совпадать.
- Значения справочников и идентификаторы звуков, функций, приложений, маршрутов, навыков, календарей и списков получай через `isivr_operations` / `isivr_call` или из существующих блоков. Не выдумывай ID.
- Для формата, который уже описан в blocks.md, используй это описание. Для ещё не описанного возьми `params` живого блока того же типа через `isivr_get_module` и перенеси структуру, заменяя только необходимые значения.
- Не меняй динамические данные, функции, контент, публикацию или серверные настройки без прямого запроса пользователя.

## Читаемая схема

- Основной успешный путь веди сверху вниз. Блок с одним выходом стоит по центру следующего, чтобы стрелка была вертикальной.
- Блок стоит ниже всех блоков, из которых в него есть переход, чтобы стрелки шли сверху вниз. Общий блок вроде `InfinityWait` не остаётся в одном ряду со своими источниками.
- Переход между блоками одного ряда не рисуй вдоль ряда. Если цель может опуститься, поставь её ниже источника по центру, чтобы стрелка была вертикальной. Если цель должна остаться в своей ветви, поставь `GoTo` под источником, а непосредственно перед целью — `Marker`.
- Стрелка не проходит сквозь блоки промежуточного ряда. Если между источником и целью нет свободного вертикального коридора, замени это ребро ближайшим `GoTo` на метку у цели.
- Если в блок входит несколько переходов, особенно с разных уровней, в него ведёт только `Marker`, стоящий прямо над ним. У источников — `GoTo` на эту метку. Соседние блоки одного ряда, которые ссылаются на одну и ту же метку, делят один `GoTo`: их выходы сходятся в него. Отдельный `GoTo` остаётся, когда между блоками стоит другой блок.
- Пустое место допустимо. Если это убирает пересечения, раздвигай уровни и смещай блок ниже. Особенно это касается `DtmfMenu`: горизонтальные линии его стека выходов не должны идти сквозь дочерние блоки соседей по ряду, поэтому такое меню опускай ниже их поддеревьев.
- `Marker` ставь над целью по центру. Его выход внизу, поэтому метка сбоку даёт ломаную стрелку.
- Ветви вертикального стека, как у `DtmfMenu`, ставь правее исходного блока: схема идёт слева направо, верхний выход — правый блок.
- Повторяющиеся возвраты и общий терминал оформляй через `Marker` + `GoTo`, а не длинной стрелкой через схему.
- Если точка входа уже отмечена `Marker`, каждый переход в эту точку идёт через свой `GoTo` на эту метку. Дальше ведёт только выход метки. `GoTo` ставь рядом с блоком, чей выход он обслуживает; несколько выходов одного блока могут делить один ближайший `GoTo`. Далёкий общий `GoTo`, к которому стрелки идут через схему, раздели.
- Ширину блока подгоняй под текст имени: не меньше каталожного размера и не меньше самой надписи, около 13px на символ плюс поля. Имя не должно вылезать на соседний блок.
- Давай блокам предметные имена: `Проверить рабочее время`, `Меню выбора продукта`, `Перевести в КЦ`.
- Не создавай пересекающиеся связи вручную. Раскладку делает `isivr_save_module`.
- При локальной правке сохраняй координаты существующих блоков.

## Проверка перед завершением

- [ ] Вся логика в корневом модуле: нет новых `Transfer`, `Designer_GetModulesSelectData` с `onlyUsed: true` возвращает один модуль.
- [ ] Есть один `Start`, все достижимые ветви имеют осмысленное завершение.
- [ ] Нет ссылок на отсутствующие блоки и неподключённых обязательных выходов.
- [ ] DTMF-кнопки, `NoInput` и `NoMatch` настроены.
- [ ] Переменные существуют и имеют совместимые типы.
- [ ] `End` и `EndCall` выбраны по требуемой семантике.
- [ ] Справочные ID подтверждены API.
- [ ] Интеграции сделаны через существующие функции; их входы, выходы и ошибки обработаны.
- [ ] `isivr_save_module` вернул успешную валидацию.
- [ ] В точку с меткой не входят прямые стрелки через схему: все такие переходы идут через ближайший `GoTo`.
- [ ] Ни одна стрелка не идёт снизу вверх: цель стоит ниже каждого своего источника.
- [ ] Нет стрелок вдоль одного ряда и сквозь блоки промежуточного уровня.
- [ ] В блок с несколькими входами ведёт только метка над ним.
- [ ] Соседние блоки одного ряда на одну метку делят один `GoTo`.
- [ ] Имя блока помещается в его ширину.
- [ ] Повторное чтение сохранило логику и ожидаемую раскладку.
- [ ] Стабилизация и публикация выполняются только по отдельному явному запросу.
