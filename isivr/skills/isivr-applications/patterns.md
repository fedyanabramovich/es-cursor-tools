# Паттерны опубликованных приложений

Источник — полный снимок стенда: 97 опубликованных приложений, 97 модулей, 635 блоков;
все модули прочитаны без ошибок. Среди них есть QA-, нагрузочные и тестовые сценарии,
поэтому факт публикации подтверждает совместимость структуры, но не качество бизнес-логики.
Для обновления снимка выполни:

```bash
node .cursor/skills/isivr-applications/scripts/analyze-active-apps.js
```

Скрипт только читает API и выводит JSON в stdout.

## Подтверждённые базовые правила

- `Start` присутствует во всех 97 модулях.
- Для завершения используются разные семантики: `End` встречается в 56 модулях,
  `EndCall` — в 34; выбирать их взаимозаменяемо нельзя.
- `AnswerCall` стоит непосредственно после `Start` в 44 модулях.
- `InfinityWait` используется в 54 модулях, преимущественно после асинхронного действия.
- На стенде почти все переменные строковые: 179 из 180. Это наблюдение, а не ограничение
  платформы; для EWT и ID приложения всё равно используй `int`, где требует блок.

## Входящий IVR с DTMF

Базовая композиция:

```text
Start -> AnswerCall -> DtmfMenu
                           ├─ 1..# -> действие/подменю
                           ├─ NoInput -> повтор или End
                           └─ NoMatch -> повтор или End
```

`Start -> AnswerCall -> DtmfMenu -> End` — самая частая пользовательская цепочка
(12 модулей). В 19 модулях есть меню, всего 37 блоков меню: вложенные меню нормальны.

Практика:

- подключай только озвученные кнопки;
- всегда обрабатывай `NoInput` и `NoMatch`;
- для повторного показа меню используй `Marker` + `GoTo`;
- ограничивай число попыток, чтобы не получить бесконечный цикл;
- аварийный `End` завершает модуль, `EndCall` — весь звонок.

## Сбор и проверка номера

```text
AnswerCall -> InputField
                 ├─ success -> Function/CC/CC_IPN
                 ├─ NoInput -> сообщение -> End
                 └─ NoMatch -> сообщение -> повтор/End
```

Подтверждено пятью опубликованными модулями. Результат сначала записывается в строковую
переменную, затем передаётся функции или телефонии. Валидацию выбирай по задаче:
длина для номера фиксированного формата, диапазон для ограниченного набора, regex для
структурного формата.

## Перевод в IPN

Минимальная композиция:

```text
Start -> AnswerCall -> CC_IPN
                          ├─ connected -> InfinityWait
                          └─ enqueued -> Sound/EWT/SetTimer
```

Переход `CC_IPN.connected -> InfinityWait` встречается 21 раз. Ветка `enqueued`
16 раз ведёт к `Sound`, ещё три — к `SetTimer`. Не завершай `connected` обычным `End`,
пока разговор агента должен продолжаться.

Для маршрутизации по номеру:

```text
AnswerCall -> DefRouting -> CC_IPN -> InfinityWait
```

`DefRouting` заполняет skill, route и EWT-app в типизированные переменные; затем передай
их в `CC_IPN`.

## Внешний вызов

```text
AnswerCall -> CC
                ├─ disconnected -> End
                └─ fail -> сообщение/резервный маршрут/End
```

`CC.disconnected -> End` и `CC.fail -> End` встречаются по 14 раз. Для рабочего
сценария обе ветви обязательны. В fallback допустим повтор через `GoTo`, но он должен
быть ограничен счётчиком/условием.

## Таймаут параллельного ожидания

Самая частая стартовая цепочка на стенде:

```text
Start -> SetTimer
            ├─ Before -> InfinityWait
            └─ After -> EndCall
```

Она встречается 18 раз; `SetTimer.Before -> InfinityWait` — 19 раз,
`SetTimer.After -> EndCall` — 17. Это шаблон watchdog: сценарий ждёт внешнее событие,
но гарантированно завершает зависший вызов после таймаута.

Если таймер больше не нужен, сбрось его через `ResetTimer`. Не переиспользуй один
`TimerID` для независимых параллельных задач.

## Декомпозиция приложений

```text
AnswerCall -> TransferToApp -> InfinityWait
```

Композиция встречается восемь раз; всего `TransferToApp` есть в 23 модулях.
`TransferToApp -> InfinityWait` встречается 28 раз. Такой терминал уместен при передаче
управления или асинхронной дочерней логике. Если `TransferControl: false`, подключи
выход к продолжению родителя вместо безусловного ожидания.

Передаваемые параметры именуй точно как входы дочернего приложения. Не связывай
приложения циклом без явной защиты от рекурсии.

## Функция и условная маршрутизация

```text
Function -> Condition
              ├─ true/именованные условия -> целевой маршрут
              └─ false -> fallback
```

`Function -> Condition` встречается 10 раз; `Function` используется в девяти,
`Condition` — в 11 модулях. Сначала запиши выход функции в переменную, затем проверяй
её в `Condition`. Fallback должен обрабатывать timeout, пустой и неожиданный ответ,
а не только положительный бизнес-результат.

## Динамические данные

- `DynamicParams` загружает оперативно изменяемые значения и используется перед
  `Condition`/`Function`.
- `ListCheck` разделяет ветви `Contain` и `NoContain`.
- `DataChange` имеет обязательные `Successfully`/`Unsuccessfully` и меняет общие данные.

Эти блоки редки в текущем снимке (3 модуля с динамическими параметрами, 2 со списком,
1 с изменением), поэтому для их структуры читай рабочий модуль полностью и не
обобщай одно значение ID на другое приложение.

## Визуальная композиция

- Главная успешная цепочка идёт вертикально сверху вниз.
- `false`, ошибка и таймаут располагаются слева; успешные/основные ветви — справа
  или продолжают центральную ось.
- Выходы `DtmfMenu` рисуются столбиком сверху вниз: `1..9,0,*,#`, затем «Таймаут» и «Ошибка». Их цели стоят правее самого меню и идут справа налево: верхний выход — правый блок.
- Блок с единственным выходом и его продолжение выровнены по центру, стрелка между ними вертикальная.
- Цель перехода стоит ниже всех своих источников. Общее `InfinityWait` не ставится
  в один ряд с очередями, звуками и переводами, которые в него входят.
- Связь двух блоков одного ряда не проводится вдоль этого ряда. Цель опускается
  ниже и выравнивается по центру источника. Если она должна остаться в ветви
  более раннего выхода, у источника ставится `GoTo`, а перед целью — `Marker`.
- Ребро не пересекает блоки промежуточного ряда. Нет свободного вертикального
  коридора — ребро заменяется ближайшим `GoTo` на метку у цели.
- Блок с несколькими входами, особенно с разных уровней, получает `Marker` прямо
  над собой, а источники — `GoTo` на эту метку. Соседние блоки одного ряда на одну
  метку делят один `GoTo`, и выходы сходятся в него. Пример: три стоящих подряд
  перевода в `InfinityWait`. Свой `GoTo` остаётся, если между блоками стоит другой.
- Ширина блока вмещает его имя и не меньше каталожной. Длинное имя вроде
  «Перевод на QA: Тестовое приложение 1» расширяет блок, а не рисуется поверх соседа.
- Расстояние между уровнями увеличивается, если это убирает пересечения.
  Горизонтальные линии стека `DtmfMenu` проходят по свободной полосе. Поэтому
  меню, стоящее в одном ряду с соседями, у которых есть дочерние блоки, опускается
  ниже их поддеревьев, а вертикаль к нему идёт по пустой колонке.
- Общие терминалы можно визуально объединять, но каждое ребро должно оставаться читаемым.
- Возврат к меню выполняется через находящийся рядом `GoTo`; его парный `Marker`
  размещается над повторяемым участком.
- Общий терминал вроде `End` тоже входит через `Marker`. Каждый выход, который
  должен попасть в эту точку, подключается к ближайшему `GoTo` на ту же метку.
  Прямая стрелка к терминалу через схему не остаётся, даже если часть выходов
  уже идёт через метку. Выходы одного блока делят один `GoTo`, дальний общий
  переход разделяется.
- Новые блоки в существующей схеме раскладываются через `incremental`; полная
  перераскладка не должна уничтожать ручную группировку стабильной схемы.

## Покрытие снимка

В опубликованных модулях встречены `Start`, `End`, `EndCall`, `InfinityWait`,
`AnswerCall`, `Sound`, `DtmfMenu`, `TransferToApp`, `SetTimer`, `CC_IPN`, `CC`,
`GoTo`, `Condition`, `Function`, `Marker`, `InputField`, `DefRouting`,
`DynamicParams`, `ListCheck`, `DataChange`, `PlayEWT`.

Не встречены `Record`, `StopChannel`, `ResetTimer`, `Calendar`, `HolidayPeriod`,
`SIPHeader` и `Transfer`. Их параметры и смысл выходов — в blocks.md.
Идентификаторы бери операциями MCP. Не восстанавливай формат по исходникам платформы.
